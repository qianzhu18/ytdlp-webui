# 1800+ 个视频网站，被我接进了自己的知识库

以前我很喜欢收藏视频。

B 站上看到一个不错的访谈，先收藏；YouTube 上遇到一个讲得很清楚的课程，先收藏；抖音里刷到一个有启发的观点，还是先收藏。

收藏夹越来越满，真正回看的视频却没有多少。

问题后来慢慢变得很具体：我不是缺内容，我是没有把内容放进自己的系统里。

所以最近我做了一个工具，叫幕库 Muku。

我之前介绍它时，总说“支持 B站、YouTube、抖音”。这句话没错，但后来我才意识到，它把幕库真正能接住的范围说小了。

**1800+。** 这是幕库底层接入的 yt-dlp 视频解析器生态规模。完整视频链接都可以先尝试进入这条处理链路。B站、YouTube、抖音是我重点适配的主链路；其他 yt-dlp 能解析的站点，只要能拿到字幕或音频，后面的整理就能继续跑。

它做的事情其实很具体：把知识视频或本地音频，整理成以后还能搜索、连接和继续使用的 Markdown 文件。

一条视频处理完成后，通常会得到几类东西：

- 原始逐字稿：保留转写得到的原始文本
- 清洗后的逐字稿：去掉口语重复，让内容更容易阅读
- 解析稿：按提示词整理成结构化文章
- 知识库稿：适合继续放进 Obsidian、RAG 或其他知识库

我比较在意的是，它不是“下载完视频就结束”的工具。

它会优先尝试获取平台字幕。字幕拿不到，再回退到音频转写。这样做不一定每次都成功，但至少处理路径是清楚的：先尽量使用已有文本，实在没有，再调用模型处理音频。

这条链路也可以批量跑。给它一份 URL 列表，配合 JSON、路径输出和断点续跑，就可以把一个系列、一个课程或一批访谈慢慢收进本地知识库。

所以“1800+”对我来说不只是一个适合放在首页的大数字。它真正意味着的是：幕库不需要给每个平台重写一套知识处理逻辑。输入端复用 yt-dlp 持续维护的解析器生态，后面继续走同一套字幕、转写、清洗和 Markdown 生成链路。

为了让第一次使用不要卡在配置上，我又补了一个本地引导：

```bash
curl -fsSL https://raw.githubusercontent.com/qianzhu18/Muku/main/scripts/install-muku | bash
muku quickstart
```

安装器会把 CLI 和 AI-agent Skill 一起装好。`muku quickstart` 会提示输入自己的 OpenRouter Key，选择默认保存目录，检查 ffmpeg 和 yt-dlp，然后启动本地 Web UI。

Windows PowerShell 也有对应的安装脚本。

这里有两条边界需要说清楚。

第一，Muku 是本地优先，不是纯离线。文件、配置和最终产物默认留在自己的电脑里，但转写和 AI 整理阶段仍然会调用你自己选择的 AI 服务。API Key 和 Cookies 应该由每个人自己配置，不要把它们放进仓库或帖子里。

第二，1800+ 来自 yt-dlp 当前的解析器范围，不是我手工测完了 1800+ 个站，更不是每条链接都保证成功。站点会改版，登录态会过期，网络、地区、DRM 和平台风控都会影响结果。最可靠的判断方式，还是拿一条自己的真实链接跑一次。

Muku 现在也还是 v0.x。它已经能跑通从视频输入到 Markdown 知识资产的主链路，但不是一个已经封死的最终产品。下载、字幕、转写、清洗、解析和知识库生成被拆开之后，后面还可以继续接更多平台、模型、模板，以及更轻量的桌面端、浏览器和 agent 入口。

我现在越来越觉得，个人知识库真正缺的不是再收藏一个工具，而是把“看见内容”到“以后还能找到并继续使用”之间的那段路补上。

Muku 只是把这段路先跑通了一个版本。它不需要先变成一个“什么都能做”的大工具，才开始有用。

先让一条视频真正进入自己的系统，后面的迭代才会有方向。
